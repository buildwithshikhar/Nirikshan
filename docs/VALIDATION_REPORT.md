## 1. Scope

In scope: the evidence-to-clip pipeline as implemented through P4 (identify vendor, vendor parsers for Dahua DHAV frames, Hikvision and Honeywell, generic H.264/H.265 carving, `ffmpeg -c copy` MP4 export with a decode test, per-clip hashes), measured on generated images with byte-comparison ground truth.

Out of scope and **not measured here**: real DVR/NVR images, firmware variation, vendor encryption modes, timestamp normalization (P5, in progress), analytics triage (P6, in progress), the court-style report (P7, planned), acquisition from physical disks, DHFS (Dahua file system) internals (not parsed), H.265 inside vendor containers, throughput on cold disks.

Tier status carried by the code and the plan: Hikvision B, Dahua B, Honeywell B; CP Plus, Uniview, TP-Link, Godrej, Matrix C. Nothing in this report changes a tier.

## 2. Method

- **Images.** Built from a seeded `random.Random` (seed 20260101; per-trial seed derived from the seed, scenario group and trial index by SHA-256). The same seed gives the same image SHA-256 (covered by a test). Every image begins with a 256-byte banner `NIRIKSHAN SYNTHETIC TEST IMAGE - NOT REAL DVR DATA` and every manifest carries `"synthetic": true`.
- **Video content.** Six ffmpeg `testsrc2` encodes (H.264 baseline, main with B-frames, high; H.265 main). Pool recorded in the results:

|---|---|---|
| h264_base_320 | 50 | `1d4b82303c2ef1d78ddff0fbfbac09a7140ccb64e450e3445722658ca8a45020` |
| h264_main_b_352 | 50 | `3c33cf3e03b829172c0f7e22fc1c76433f26de26cb6b9d4a47d63d1d60fc74af` |
| h264_high_480 | 50 | `845dc71ac725192e17c8eccbc18ea790d40823871379cce165575fbecd59ab8d` |
| h264_base_256 | 75 | `4e9e353fae4f7f61fafdb9986e6cbe72b1276cb2b8b546c9e893e37b45ec0a80` |
| h265_main_320 | 50 | `c86c8e10c90c85facac744deadec28572fcb69f88c853b12600fdebcef36e9a5` |
| h265_main_416 | 50 | `97476ea4a03b610954bfbbe092a7f95bd758e1f49cd8db3dc9f0ddb921b86d33` |

- **Ground truth** is computed from the finished image by byte comparison, not from intentions. A clip NAL unit is *intact* if its bytes equal the source; a VCL NAL unit is *recoverable* if it, its GOP's parameter sets and every earlier VCL NAL of its GOP survived.
- **Metrics** (micro-averaged over trials; k/n with Wilson 95% interval in brackets, in percent). *Clip recall*: at least 50% of a clip's recoverable frames recovered. *Clip precision*: carved clips with at least 50% of their bytes inside an expected truth clip. *Byte-exact*: carved extents equal truth extents (zero-only boundary differences ignored). *Frame recall/precision*: VCL NAL units lying inside carved extents; this is **NAL coverage, not decoder output**. *Decode ok*: the carved bitstream decodes without ffmpeg errors. *Hash integrity*: the recorded bitstream SHA-256 equals a recomputation from the image bytes at the recorded extents and the MP4 file hash matches.
- **Negatives** must produce no clip that decodes cleanly; clips emitted anyway must be flagged `decode_errors` or `export_failed`.
- **Vendor-layout scenarios** (`@dhav`, `@hik`, `@honeywell`) run the generic carver, the vendor parser, and parser-then-generic ("`vendor+generic`", the production pipeline order), and cross-check parser output against the generic carver.
- **Regression guard.** `app/validation/thresholds.json` holds floors and ceilings, enforced by `tests/test_validation.py`; strict mode fails if a scenario is missing from a full run. Violations recorded in this baseline: 0.
- Environment: ffmpeg version 9.0.2 Copyright (c) 2000-2026 the FFmpeg developers.

| `fragmented_zero_join_on` | 3 | 0 | 38 | 38 |

Measured false-accept rate on the decoy scenario: 11.8% (35/297) [9-16] (percent, k/n, 95% interval). `docs/VALIDATION.md` and the plan quote 11.8% (35/297, 95% CI 9-16%). The design reason is a 4-bit `frame_num`, giving roughly 1-in-8 wrong candidates passing the continuity test. Reassembly therefore stays off unless the examiner enables a join gap, and joined clips are labelled `reassembled`.

## 5. Findings

Each finding is limited to what the tables above support.

1. **Pipeline works on modelled inputs.** Clean, deleted-intact and zero-gapped clips in the raw layout are recovered with byte-exact extents and matching hashes (section 3.3). This is expected: the scenarios and the carver were developed together.
2. **A clean decode does not prove a clip is byte-faithful.** With random non-zero garbage between NAL units the generic carver absorbs the garbage (byte-exact 0%) while ffmpeg still decodes the clips (decode ok 100%). Examiners must not treat "decode ok" as "unaltered".
3. **Documented limits are pinned, not hidden.** Zero padding wider than `max_pad` (64 bytes by default) inside a clip loses the clip (`zero_pad_inside_wide`). Fully overwritten clips do not appear. Multi-channel images without channel metadata mix cameras in the generic carver (`multi_channel_gop`, `multi_channel_frame` clip precision).
4. **Vendor headers help the parser.** On the DHAV and Honeywell layouts the parser bounds payloads by the header length, restoring byte-exact extents that the generic carver cannot reach. This follows from the layout we wrote and is not evidence about real recorders.
5. **The parser is blind to cleared metadata.** On `deleted_intact_zero@hik` the Hikvision parser alone recovers only the clips whose HIKBTREE entries survive; the generic carver recovers all. The production order (parser, then generic over uncovered ranges) keeps both (`hikvision+generic` rows).
6. **Cross-check disagreements are listed, not resolved.** Frequent `parser_clip_not_found_by_generic` rows on the DHAV layout were not investigated one by one in the baseline.
7. **Encrypted slices behind clear parameter sets still emit clips**, all flagged as decode failures.
8. **The parser is not uniformly better.** On `fragmented_zero_join_on@dhav` the Dahua parser's frame recall is lower than the generic carver's with reassembly on (section 4.1), because parser clips are bounded by DHAV frames and are not reassembled across gaps. On the Hikvision layout the parser and generic carver tie on every scenario except `deleted_intact_zero@hik`. Layout simplicity (clips start at block boundaries) is a likely reason; that is a hypothesis about our layout, not a measured cause.

## 6. Defects found by the harness and fixed

From `docs/VALIDATION.md` ("Defects the harness found during development"):

- Fake parameter-set groups (random bytes behind SPS/PPS/IDR headers) produced 64 false-positive clips in two adversarial images and 384 in two noise images. Fixed with SPS/PPS/VPS syntax validation and a "slice must reference a PPS from the clip" rule (`validate_params`, default on). **Risk:** a real device with non-standard parameter sets could be rejected; the option can be disabled per run and this has not been exercised on real streams.
- A lone zero byte at the end of an image was included in the last NAL (fixed).
- A positional-argument shift silently dropped the Dahua engine from the first parser baseline and the threshold checker skipped the missing scenarios (fixed; strict mode now fails on missing scenarios).
- A scenario modelling flaw wrote a "newer recording" as raw bytes into DHAV-layout images, which a DHAV parser correctly could not see; the cross-check exposed it and the generator now writes it in the image's own layout.
- Scorer artefacts (ties between a destroyed clip and its overwriter, zero-byte boundary ambiguity) were fixed in the scorer, not in the carver.
- Round A carver change: an invalid NAL header within `max_pad` bytes of the last valid NAL is tolerated as stray junk, because vendor header fields are not emulation-escaped and can contain `00 00 01`. This improved generic frame recall on the DHAV and Honeywell layouts and left adversarial and negative scenarios unchanged (`docs/ARCHITECTURE.md`, "Parser-first pipeline"). Note: the prose figures in `docs/VALIDATION.md` for the generic carver on the DHAV layout (frame recall 85%) predate this change; use the tables in this report, which come from the current `results.json`.

## 7. Limits of this validation

- Vendor-layout results are circular (layout and parser come from the same documents).
- All inputs are synthetic and come mostly from one encoder family (x264/x265) with `testsrc2` content.
- Scenario parameters were chosen by us, and the carver rules and the scenarios were developed together, so passing is expected.
- Frame-level numbers measure NAL coverage inside carved extents, not decoded pictures, wall-clock time or channel attribution.
- Durations of exported clips are nominal (stream frame rate), not recording time.
- Real-device performance, firmware variation, vendor encryption, DHFS, H.265 vendor layouts and timestamp semantics are untested.
- Author-reported recovery figures in the literature (RESEARCH.md, sources S7 and S8, abstracts only) are unreplicated and are not used here.

## Appendix A. Table extraction

The tables above were produced by reading `docs/validation/results.json` (`scenarios[].metrics.<name>.{k,n,rate,ci95}`, `scenarios[].counts`, `scenarios[].crosscheck_disagreements`) and formatting each as `rate% (k/n) [lo-hi]`. Core of the script:

```python
import json
d = json.load(open("docs/validation/results.json"))
def fmt(m):
    if m is None or m["n"] == 0: return "n/a"
    lo, hi = m["ci95"]
    return f"{m['rate']*100:.1f}% ({m['k']}/{m['n']}) [{lo*100:.0f}-{hi*100:.0f}]"
for s in d["scenarios"]:
    print(s["id"], [fmt(s["metrics"].get(c)) for c in
          ("clip_recall","clip_precision","byte_exact","frame_recall","frame_precision","decode_ok","hash_integrity")])
```
