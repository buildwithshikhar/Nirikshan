# Validation (SYNTHETIC)

> **Page-1 statement.** Every number in this document comes from images generated by Nirikshan's own harness. Synthetic scores prove that the pipeline works on the layouts we modelled; they do **not** predict performance on real DVR/NVR images. A parser built from a paper's layout and tested on images generated from the same layout is a **circular check, not independent validation**. No vendor is Tier A.

Full tables: [validation/results.md](validation/results.md) (human) and [validation/results.json](validation/results.json) (machine; carries a digest that excludes timings). Regenerate with `make validate` (about 80 s, needs ffmpeg and `backend/.venv`); `make validate-quick` runs 3 trials per scenario. Code: `backend/app/validation/`. Regression floors/ceilings: `backend/app/validation/thresholds.json`, enforced by `tests/test_validation.py` (fresh 3-trial run plus integrity of the committed baseline).

## Method
- **Images.** Built from a seeded `random.Random` (seed `20260101`; per-trial seed = SHA-256 of seed, scenario group and trial index). The same seed gives the same image SHA-256 (tested). Every image starts with a 256-byte `NIRIKSHAN SYNTHETIC TEST IMAGE - NOT REAL DVR DATA` banner; every manifest has `"synthetic": true`. Video comes from ffmpeg `testsrc2` encodes (6 variants: H.264 baseline/main+B-frames/high, H.265 main); the pool's SHA-256s and the ffmpeg version are recorded in the results.
- **Layouts.** P3 images use the `raw` layout (clips placed in a generic image, no vendor structures). Vendor-layout variants arrive with the P4 parsers and are labeled "per-paper layout, not a real device image".
- **Ground truth** is computed from the finished image by byte comparison, not from intentions: a clip NAL unit is *intact* if its bytes equal the source; a VCL NAL is *recoverable* if it, its GOP's parameter sets and every earlier VCL NAL of its GOP survived.
- **Metrics** (micro-averaged over trials, k/n with Wilson 95% intervals): *clip recall* (>= 50% of a clip's recoverable frames recovered); *clip precision* (carved clips with >= 50% of their bytes inside an expected truth clip); *byte-exact* (carved extents equal truth extents, ignoring zero-only boundary differences); *frame recall/precision* (VCL NAL units lying inside carved extents; this is NAL coverage, not decoder output); *decode ok* (carved bitstream decodes without ffmpeg errors); *hash integrity* (the recorded bitstream SHA-256 equals a recomputation from the image bytes at the recorded extents, and the MP4 file hash matches).
- **Negative classes** must produce no clip that decodes cleanly. Clips that are emitted anyway must be flagged `decode_errors`/`export_failed`; the counts are reported, not hidden.

## What the baseline shows (seed 20260101, 20 trials, synthetic)
- Clean, deleted-intact and zero-gapped clips: clip recall 100.0% (60/60), byte-exact 100.0% (60/60) for zero gaps, hash integrity 100.0% (60/60).
- Zero padding inside a clip is handled up to the 64-byte `max_pad` (byte-exact 100.0% (40/40)); 100-300 byte padding loses everything (frame recall 0.0% (0/2175)). This is a documented limit and is pinned in the thresholds file.
- Random (non-zero) garbage is absorbed into the preceding NAL: frame recall 100.0% (3200/3200) but byte-exact 0.0% (0/60). ffmpeg still decodes those clips cleanly (decode ok 100.0% (60/60)), so **a clean decode does not prove a clip is byte-faithful**.
- Partial overwrite: recoverable frames are found (frame recall 100.0% (1511/1511) for zero overwrite); fully overwritten clips do not appear (clip precision 100.0% (26/26)).
- **Fragment reassembler (H.264 heuristic):** with zero-gap fragments it recovers frames (96.8% (1089/1125) vs 81.0% (911/1125) with reassembly off) and accepted all correct joins; when the next fragment of another recording is a decoy it **falsely accepts 11.8% (35/297, 95% CI 9-16%)** of wrong candidates. It is therefore off by default and joined clips are labeled.
- **Multi-channel without channel metadata** fails for the generic carver: clip precision 40.0% (8/20) (GOP-interleaved) and 30.0% (6/20) (frame-interleaved) because clips mix cameras, although every frame is covered.
- **Negatives:** nothing decodes cleanly in any negative class. Encrypted slices with clear parameter sets still emit clips in most images (18 clips over 20 images); every one is flagged as a failed decode. MJPEG, MPEG-4 Part 2, whole-stream encryption, encrypted payloads with encrypted parameter sets, and noise with false start codes emit nothing.

## Defects the harness found during development (fixed)
- Fake parameter-set groups (random bytes behind SPS/PPS/IDR headers) produced 64 false-positive clips in two adversarial images and 384 in two noise images. Fixed with SPS/PPS/VPS syntax validation and a "slice must reference a PPS from the clip" rule (`validate_params`, default on). Risk: a real device with non-standard parameter sets would be rejected; the option can be switched off per run (`validate_params=false`) and this has not been exercised on real streams.
- A lone zero byte at the end of an image was included in the last NAL (fixed).
- Scorer artifacts (ties between a destroyed clip and the clip that overwrote it, zero-byte boundary ambiguity) were fixed in the scorer, not in the carver.

## Limits of this validation
- All inputs are synthetic and mostly generated by one encoder family (x264/x265) with `testsrc2` content.
- Scenario parameters were chosen by us; the carver's rules and the scenarios were developed together, so passing is expected.
- Frame-level numbers measure NAL coverage inside carved extents, not decoded pictures, and not wall-clock or channel attribution.
- Real-device performance, firmware variation and vendor encryption are untested.
